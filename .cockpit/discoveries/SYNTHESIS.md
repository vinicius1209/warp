# Cockpit — Assessment Synthesis (2026-06)

## Verdict
Cockpit has a genuinely solid engineering foundation but is, as a product, still a developer's terminal wearing a thin mission costume — it is not yet the guard-railed, incredible-UI tool a non-dev vibe coder needs. The mission system's bones are clean (templates, staged scaffolding, gate dialog, named tab-groups), and the surrounding Warp infrastructure is unexpectedly generous: battle-tested agent-completion detection, a stable slug already on every mission, an SSE-capable HTTP client, a vendored Node runtime, and existing project/auth FTUX flows all sit ready to be wired in. The blocker is that a single root cause — binding durable mission state to the ephemeral TabGroupId that gets regenerated on every restart instead of the stable slug that already exists — produces all three audit CRITICALs, breaks the tab-group-first vision, and is the hard dependency for both planned phases; it must be fixed before anything is built on top of it. After that, the work is overwhelmingly UX and guard-rail wiring (pre-flight, visual project picker, artifact-aware gates), not new architecture: the highest-leverage product gains are cheap because the primitives exist. Sequence the binding fix and pre-flight guards first, then idle auto-gates and the signature artifact-aware gate, and treat the opencode engine as the final flag-gated track that reuses everything before it.

## Must-fix
- **[CRITICAL] Mission↔group binding keys on ephemeral TabGroupId; switch to the already-existing stable slug**
  - ActiveMission already carries `slug: String` (registry.rs:14) but the mission↔group binding, gate pending state, and pane mapping all key on `group_id: Option<TabGroupId>` — which sqlite.rs:2472 regenerates fresh on every restore. Add a `mission_slug: String` to TabGroupSnapshot and re-resolve `group_id` from slug on restore (replacing the name-matching heuristic in regroup_resumed_mission_tab). This is the single fix that resolves audit 2.1 (restore mismatch), 2.5 (gate state leak — store slug not index in mission_gate_pending_index), and tab-group report 5.6 (group instability). It also UNBLOCKS Phase 2a and 2b, both of which need a reliable terminal_view_id→mission lookup.
  - refs: app/src/missions/registry.rs:14,24,108-112; app/src/persistence/sqlite.rs:2472; app/src/workspace/view.rs:7379-7418,1041,7141
- **[CRITICAL] Mission actions advance the wrong mission via find_latest() fallback**
  - mission_next_stage (view.rs:7023-7024) falls back to registry.find_latest() when the active tab isn't in a mission group, so hitting the hotkey from a non-mission tab silently advances the most-recently-registered mission, not the intended one. Remove the find_latest fallback: if the active context maps to no mission, no-op with a toast ('Switch to a mission tab to advance it') rather than guessing. Same class of bug as keying on index — validate or refuse, never guess.
  - refs: app/src/workspace/view.rs:7017-7034
- **[CRITICAL] Mission index assumed valid after every user interaction; can act on stale/shifted index**
  - After gate confirm, Mission Control Next/Resume/Abandon, the index passed to registry.get(mission_index) can be stale (index shifts after a removal, cached button row). Once binding moves to slug (must-fix #1), pass the immutable slug through all action paths and resolve to a live index at call time, returning a user-facing toast on miss instead of a silent log::error. Add an assert_mission_by_slug(slug) -> Option<usize> helper and route every mission action through it.
  - refs: app/src/workspace/view.rs:7170-7212,7272-7295,7301-7372
- **[CRITICAL] Agent pre-flight missing: missions launch into a CLI that may be uninstalled or logged-out**
  - start_mission hardcodes default_harness='claude' (view.rs:6953) and open_mission_stage_tab spawns the PTY with zero check that the binary exists or is authed; failure mode is raw shell errors in a terminal the non-dev can't parse. This is the UX report's #1 silent-failure (Gap C). Add app/src/missions/preflight.rs: check(harness)->{Ready|NotInstalled|NotLoggedIn} via util::path::resolve_executable + a cheap auth probe, and gate Start Mission on Ready, routing NotLoggedIn into the already-built show_create_auth_secret_modal/AuthSecretFtuxView. Not strictly a correctness bug in the Rust sense, but it is the product's highest-severity failure for the actual persona and is cheap (wiring existing parts).
  - refs: app/src/workspace/view.rs:6953,7250-7259; app/src/ai/auth_secret_types.rs; app/src/ai/harness_availability.rs
- **[IMPORTANT] brief.md read swallows IO errors and corrupts the prompt silently**
  - std::fs::read_to_string(...).unwrap_or_default() (view.rs:7125,7246) returns empty on permission-denied/deleted, substituting an empty {{briefing}} into the agent prompt with no warning. Propagate the error and surface a toast; the agent should never run against a silently-empty briefing.
  - refs: app/src/workspace/view.rs:7125,7246; app/src/missions/scaffold.rs:179-185
- **[IMPORTANT] Registry, modals, and mission-lifecycle integration paths are untested**
  - registry.rs (register/advance/set_group_id/remove/find_by_group/find_latest), the three modals, and the end-to-end scaffold→gate→advance→complete flow have zero tests. Before building 2a/2b on top of this binding logic, add a registry unit-test suite and one integration test for the lifecycle including session-restore + slug re-resolution. The binding rewrite (must-fix #1) is exactly the kind of change that needs a regression net.
  - refs: app/src/missions/registry.rs; app/src/missions/mission_control_modal.rs; app/src/workspace/view.rs
- **[MINOR] Multi-window mission actions dispatch to whichever Workspace they're called on**
  - Missions assume a single Workspace per app; resume/next/abandon from Window B can operate on Window A's state or no-op. Document the single-window assumption in start_mission/mission_next_stage now (cheap), and defer the real multi-window refactor — it is not on the critical path for the non-dev product and the MultiWorkspace infra is still underdeveloped.
  - refs: app/src/workspace/view.rs:6911-6994; app/src/missions/mission_control_modal.rs

## Roadmap
- [0 must-fix-foundation] (impact high/effort M) Stable slug-based mission binding + slug-keyed gate state + assert_mission_by_slug() router + registry/lifecycle test suite
  - Resolves all three audit CRITICALs and tab-group gap 5.6 at once, and is the hard dependency for 2a, 2b, and persistent UX. The slug already exists on ActiveMission — this is plumbing + tests, not redesign. Nothing durable should be built on the ephemeral-ID foundation.
- [1 guard-rails] (impact high/effort M) Harness pre-flight: preflight.rs (Ready/NotInstalled/NotLoggedIn) + auto-select first Ready harness, gate Start Mission, route NotLoggedIn into existing AuthSecretFtuxView
  - Closes the #1 silent-failure for the persona (launch into a broken CLI). Mostly wiring existing parts: resolve_executable, the Harness enum, show_create_auth_secret_modal. Without it, every downstream UX polish still ends in unparseable shell errors. Must precede idle-detection and opencode so completion logic never runs against a dead harness.
- [1 guard-rails] (impact high/effort S) Visual project picker replacing the path text field in start_mission_modal (recent projects from ProjectManagementModel + folders-only file picker)
  - Closes the hardest wall in the whole flow (Gap B: typing absolute paths). Low effort because ProjectManagementModel/SuggestedProjectsDataSource and the folders-only picker are already wired in welcome_view.rs — it's a swap of dir_editor for a list, deleting the validation/error branch entirely. Pairs naturally with pre-flight in the same modal pass.
- [2a idle-gates (prep)] (impact high/effort S) StageStatus::Failed + Waiting variants + agent-error detection wired to mission stage state
  - Prerequisite for both idle auto-gates (need to distinguish Success/Blocked/Failed) and richer Mission Control (live status). Currently StageStatus is only Pending/Running/Done, so errors are invisible (Gap G). Small enum + manifest change that unblocks two larger increments.
- [2a idle-gates] (impact high/effort M) Idle auto-gate: subscribe Workspace to CLIAgentSessionsModel Success, map terminal_view_id→mission via slug binding, auto-trigger gate or auto-advance per template auto_advance flag, with is_agent_supported guard + debounce
  - Headline workflow win — no more guessing when the agent finished. Detection machinery is production-ready and the AgentNotificationsModel proves the exact signal path. Gated on increment 0 (reliable pane→mission map) and increment 3 (Failed/Waiting states). Additive and flag-defaulted to manual, so zero regression risk to existing templates.
- [UX signature] (impact high/effort M) Artifact-aware gate dialog: preview the produced spec.md/review.md inline; Approve / Ask-for-changes(note→re-run) / Redo instead of Continue/Cancel
  - This IS the methodology's payoff and the core trust mechanism — turns 'approve blind' into 'review what was made.' Builds on gate_dialog.rs + the artifacts templates already write to {{mission_dir}}. Slots after idle-gates because the gate now also fires automatically, so making it informative compounds. Reuse markdown_parser for the preview.
- [UX cockpit] (impact high/effort L) Richer Mission Control: per-mission progress bar, stage timeline pills, live agent status, contextual single primary action (Continue/Review/Retry), illustrated empty state
  - Converts the debug-view text wall into an actual cockpit; the trust surface a budget-conscious founder lives in. Depends on Failed/Waiting states (increment 3) and idle status signals (increment 5). Cost/token meter can be a follow-up once per-group usage aggregation lands.
- [UX polish] (impact medium/effort S) Template cards with plain-language pitch/best-for/stage-summaries + abandon-confirmation dialog (quick polish wins)
  - Makes methodology choice legible (Gap D) and prevents accidental mission loss. Low effort: extend templates.rs YAML with #[serde(default)] pitch/best_for/summary fields (existing templates keep parsing) and wrap Abandon in the existing Dialog pattern. Can slot anytime after the modal is touched for the project picker.
- [tab-group-first] (impact medium/effort L) Tab-group metadata + group-first sidebar: project_root/git_branch/default_harness on TabGroup, mission status in group header, group palette (Cmd+K to jump)
  - Realizes the 'project IS the workspace' pillar. Now safe to build because group identity is stable (increment 0). Extends TabGroup + TabGroupSnapshot and the vertical_tabs/horizontal renderers. High value but large surface, and the mission flow delivers more per-unit-effort first, so it sequences after the UX cockpit.
- [UX front-door] (impact medium/effort M) Mission Home as first screen: hero 'Start a Mission', Continue cards for active missions, recent-projects strip, terminal escape hatch behind a setting
  - Gives the methodology a front door (closes Gap A) and makes the group-first switcher the default surface. Best after Mission Control is rich and groups are stable, so the home screen pulls from polished surfaces rather than placeholders.
- [2b opencode] (impact medium/effort XL) Phase 2b opencode engine: OpenCodeServerManager (per-dir pooled, ephemeral port, health-gated), Rust REST+SSE client, structured OpenCodePaneView, permission dialog (Once/Always/Reject), fork open_mission_stage_tab on harness=='opencode', session.idle→auto-gate, engine-aware resume + auth FTUX
  - Delivers 'chat with guards and incredible UI' beyond a PTY and unlocks subscription-driven backends (ChatGPT-plan/Copilot/Zen/Ollama). Largest surface (process supervisor + SSE state machine + new pane type); ship as its own sub-phased track (P2b.0 pre-flight → .5 mission integration). Sequenced last because it's flag-gated, additive (PTY path untouched), and depends on the stable binding, pre-flight, Failed/Waiting states, and the artifact-aware gate all being in place — it reuses every one of them. Pin an opencode version and use #[serde(other)] Unknown on the event enum against version drift.
